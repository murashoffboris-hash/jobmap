# Правила эффективной команды разработки (JobMap Lessons Learned)

> Файл-выжимка из реального опыта проекта JobMap. Создан 27.07.2026.
> **Назначение:** давать всем оркестраторам и воркерам в следующих проектах, чтобы не наступать на те же грабли.
> **Не** — обязательный догмат. Это **набор паттернов**, которые сработали в проде.

---

## 1. Лимиты итераций — не давай воркеру умереть недоделав

### Проблема
Воркеры стабильно умирали по `iteration budget exhausted (90/90, 180 tool calls)` на сложных задачах: feature писалась, тесты проходили, но **воркер не успевал закоммитить и смерджить**. Затем на доске появлялась «мертвая» задача с неоформленным кодом. Приходилось пересоздавать.

### Решение
1. **`goal_mode=True`** в задачах, которые объективно сложные (PWA, миграции БД, инфра-деплой, фичи >1 день работы). Воркер **продолжается после лимита** в той же сессии, пока judge не согласится что готово.
2. **Сам-мерж в `infra/initial-audit`** — воркер сам делает `git checkout -b` → работа → `git merge` → smoke → `kanban_complete`. Не ждёт reviewer'а (это +1 диспетч-цикл = +1-2 часа латентности).
3. **Failure limit 2 → 4** в конфиге канбана. Транзиентные краши не должны хоронить задачу.

### Когда НЕ применять
- Простые фиксы (1-2 файла, опечатки, мелкие правки) — там goal_mode избыточен.
- Задачи где нужна обязательная независимая проверка (security-audit, важный code review) — там reviewer нужен.

## 2. Fallback-цепочки провайдеров — обязательно с первого дня

### Проблема
Дважды команда вставала целиком:
- DeepSeek переименовал модели → 8 профилей умерли разом.
- MiniMax закончились кредиты → 2 профиля умерли на 2-3 дня.

### Решение
В **каждом** `config.yaml` профиля прописать **минимум 2 провайдера** в `fallback_providers`:
```yaml
fallback_providers:
  - provider: kimi-coding
    model: kimi-k3
  - provider: minimax
    model: MiniMax-M3
```

Бюджетно: kimi-coding + minimax покрывают 90% кейсов. Если бюджет позволяет — добавить 3-й (openrouter как универсальный fallback).

## 3. Дублёры профилей — при 5+ blocked-задачах на профиль

### Проблема
`hr-backend-programmer` имел 5 blocked-задач одновременно. Пока он был занят — остальные стояли. Узкое место №2 после iteration budget.

### Решение
При 5+ blocked-задачах на специальность:
1. **Создать дублёра** профиля: `hermes profile create --clone-from hr-backend-programmer hr-backend-programmer-2`
2. **Прописать модель и провайдера** явно (клон не наследует): `hermes -p hr-backend-programmer-2 config set model.default <model>`
3. **Специализация через description**: `hermes profile describe` — это влияет на автомаршрутизацию декомпозера.
4. **Перераспределить blocked-задачи** через `hermes kanban --board X reassign <task> <profile-2>`

### Когда НЕ применять
- При <3 blocked на профиль (избыточно, размножает ошибки).
- Для security/specialist профилей (security-reviewer, code-reviewer — лучше пусть один работает, чем два мешают друг другу).

## 4. Цепочка деплоя «код → review → deploy» — сжимай до 1 диспетча

### Проблема
Каждая фича проходила 3 диспетча: программист → reviewer (merge) → devops (deploy). Латентность: 1-2 часа на каждый шаг. Типичный цикл фичи: 4-5 часов вместо 1.5.

### Решение
**Сам-мерж воркером + автотесты в build pipeline**:
1. Воркер делает `git checkout -b feature/...` от main.
2. Пишет код + тесты.
3. `git merge feature/...` в main.
4. `npm run build && npm test` — зелёные.
5. `kanban_complete`.

**Reviewer подключается только для**: security, финансовые операции, изменения схемы БД.

### Когда НЕ применять
- Если в команде больше 3 человек и есть риск конфликтов при одновременной правке одних файлов — лучше оставить reviewer.
- Для критичных PR (production) — обязательно независимая проверка.

## 5. Watchdog для инфраструктуры — cron, который молчит

### Проблема
Gateway падал 3 раза за неделю. Задачи в `ready` стояли, никто не знал. Час уходил на «а почему ничего не делается».

### Решение
1. **Cron-скрипт** с `no_agent=True` (только shell, без LLM):
   ```bash
   if hermes gateway status 2>&1 | grep -q "No gateway process"; then
     hermes gateway start
     echo "gateway restarted"
   fi
   ```
2. **Запускать каждые 5 минут**.
3. **deliver=all**, чтобы уведомление пришло если реально упал.

Если бюджет позволяет — добавить watchdog для disk, memory, ssl-renewal.

## 6. Project digest для воркеров — экономь 20-30 итераций разведки

### Проблема
Каждый новый воркер тратил 20-30 итераций на чтение `AGENTS.md`, `CLAUDE.md`, `README.md`, схем, конвенций. На простых задачах это 30% бюджета.

### Решение
Один файл `docs/Архитектура/PROJECT_DIGEST.md` (3-6 KB) с разделами:
- Назначение проекта (1 абзац)
- Ключевые пути (5-10 строк максимум)
- Архитектура (1 схема, 1 абзац)
- Команды сборки/тестов/deploy (по 1-2 команды)
- Конвенции (3-5 пунктов)
- Текущие блокеры (2-3 строки)
- **КРИТИЧНО: что НЕ делать** (3-5 пунктов, самая ценная секция)

Сослаться из `SKILL.md` оркестратора, чтобы каждый воркер читал автоматически.

### Когда НЕ применять
- Если проект одноразовый (<10 задач).
- Если digest устаревает быстрее чем его пишут (нужен выделенный documenter).

## 7. Правки nginx/proxy.conf — есть невидимые ловушки

### Проблема (конкретные случаи из JobMap)
1. **CSP-фильтр `connect-src 'self'`** забыли расширить → фронт не мог загрузить тайлы с cartodb. Чинил дважды.
2. **Апстрим указывал на порт 80** вместо реального 8080 → 502.
3. **Путь `/fonts/` указывал на мёртвый upstream** (openmaptiles.org шрифты кончились) → 0 байт.
4. **`/tiles/style.json` отдавал 404**, потому что стиль называется `jobmap`, а не `basic` (по умолчанию tileserver).

### Решение
После **каждой** правки proxy.conf:
1. `scp proxy.conf VPS:/opt/jobmap/deploy/nginx/proxy.conf`
2. `ssh VPS "docker exec jobmap-nginx nginx -t && docker restart jobmap-nginx"`
3. **Verify end-to-end** через `curl -s -o /dev/null -w "%{http_code}" http://<URL>/<path>` — не доверять «nginx -t сказал ok».
4. **CSP никогда не сужать** — лучше добавить домен в исключения чем удалить.

См. skill `orchestrator-workflow → references/deploy-tricks.md` для подробностей.

## 8. Сам-мерж правила — что нельзя делать воркеру

### Запрещено
- `git push --force` или `--amend` в main/infra-ветки
- Удаление чужой feature-ветки через `git branch -D`
- Merge в main без smoke-тестов
- `git rebase` чужих коммитов

### Обязательно
- Коммиты на русском, формат `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `infra:`
- Каждый коммит имеет осмысленное сообщение с контекстом
- `git log feature-branch..infra/initial-audit` — посмотреть нет ли расхождений

## 9. Kanban: отменяй дубликаты сразу

### Проблема
Когда фича задеплоена (например, форма создания вакансии), на доске **оставались 3-4 дубликата** этой же задачи от прошлых попыток. Воркеры путались, брали в работу мёртвую задачу, тратили время.

### Решение
**Ежедневно** (в рамках оркестраторской рутины) — пройти по `blocked` и `ready`, отменить:
- Задачи, чьи коммиты уже в main
- Задачи с parent'ом = done и тело которых выполнено
- Задачи старше 5 дней без прогресса (если не в `ready`)

```bash
hermes kanban --board X complete --metadata '{"reason":"duplicate"}' --summary "Закрыто — заменено на t_xxx (коммит Y)" t_yyy
```

## 10. Geo self-hosting — учись на ошибках JobMap

### Конкретные грабли
- **Nominatim** требует минимум 5-6 ГБ RAM на импорт. На VPS с 5.7 ГБ — **вылетает по OOM**. Решение: импорт на 2-3 ГБ или использовать образы `mediagis/nominatim:4.5` (меньше ест).
- **OSRM** — 5 минут на импорт, потом работает. Нужно 0.5 ГБ.
- **Tileserver-gl** с mbtiles — для Беларуси 350 МБ extract → 371 МБ mbtiles, 150 083 тайла. Данные обновлять **раз в месяц** (Geofabrik releases).
- **Шрифты для tileserver** (glyph PBF) — tileserver сам их не генерирует. Используют публичные (carto, maplibre-demo, openmaptiles), и **свои** через fontnik (Node.js).

### Порядок деплоя (чтобы не словить OOM)
1. Скачать pbf (~350 МБ, Geofabrik) → диск.
2. **OSRM** первым (быстрый, мало памяти).
3. **Nominatim** (долгий, требует внимания к RAM).
4. **Tileserver** (мгновенный).
5. Подключить backend (sub_filter для стиля, fonts proxy).

### Шпаргалка по proxy
```
location /tiles/  → tileserver:8080/
location /data/   → tileserver:8080/data/   (для tilejson URL в стиле)
location /fonts/  → cartodb (прокси на public CDN) — НЕ на tileserver
```

## 11. CSS фреймворк и стек — фиксируй сразу

### Проблема
В JobMap воркеры тащили разные CSS-решения (Tailwind, custom CSS, CSS-in-JS). Конфликты на этапе интеграции. **Потеряли 1 день** на унификацию.

### Решение
**На этапе создания проекта** зафиксировать в `docs/architecture/STACK.md`:
- Frontend: React + TypeScript + **только Tailwind** (или **только CSS Modules**)
- Backend: Python + FastAPI + SQLAlchemy + Pydantic v2
- DB: PostgreSQL + PostGIS (если geo)
- Build: Vite (frontend), uvicorn (backend)
- Test: Vitest + Testing Library (FE), pytest (BE)
- **Запретить** ad-hoc UI-библиотеки, кастомные стили без обсуждения

## 12. PWA / Service Worker — осторожно с кэшем

### Проблема
Воркер внедрил `vite-plugin-pwa` с Workbox → SW закешировал старые бандлы. После изменения стиля карты пользователь видел **серый фон** неделями, потому что SW не отдавал новый style.json. **Самая частая причина «у меня не работает, а у тебя работает»** в JobMap.

### Решение
1. **При каждом релизе** менять версию SW: `self.skipWaiting()` + `clientsClaim()` + `version: 'vN.M'`.
2. **Документировать** в `docs/operations/CACHE_BUSTING.md`: «после деплоя — Ctrl+Shift+R или Application → Service Workers → Unregister».
3. **Либо вообще не использовать SW** для первой версии (добавить позже, когда UI стабилен).
4. Если без SW нельзя — добавить «Update available» UI-промпт (`ReloadPrompt.tsx`).

## 13. Memory для оркестратора — собирай в один файл

### Что хранить в `~/.hermes/profiles/<name>/memory/memory.md`
- **User preferences** (язык, стиль, формат отчётов)
- **Project conventions** (VPS-доступ, секреты как называются)
- **Tool quirks** (конкретные ловушки инструментов)
- **Lessons learned** (3-5 строк после каждого инцидента)

**НЕ хранить**: PR-номера, commit SHA, статус задач, completed-work logs (использовать `session_search`).

### Формат
- Declarative facts: «User prefers concise responses» ✅
- НЕ инструкции себе: «Always respond concisely» ❌ (звучит как директива)

## 14. Cron-доставка — auto vs origin

### Проблема
Cron `jobmap-status-report` создавался с `deliver=origin` (тот же чат), но иногда не доезжал. **Не знаю почему** — возможно, конфиг теряется между обновлениями.

### Решение
При создании cron:
1. Явно указывать `deliver='all'` или `attach_to_session=true` (восстанавливает контекст).
2. **После создания** проверить через `cronjob list`, что поле `deliver` правильное.
3. **Если доставка не работает** — делать ручной доклад, не ждать следующего cron.

## 15. CI/CD — автоматизируй деплой как можно раньше

### Эффект
- 8 деплоев × 20 мин руками = 2.5 часа потерянного времени за 3 дня
- С CI/CD: 8 × 3 мин = 24 мин
- **Экономия: 2 часа за неделю** + 0 багов от забытых миграций

### Минимальный workflow
- Триггер: `push` в main
- `npm ci && npm run build`
- `rsync` через `appleboy/ssh-action`
- `docker compose up -d`
- `alembic upgrade head` (если есть)
- Smoke: `curl https://site/health`

Стоимость: 0 ₽ (GitHub Actions free tier). Время настройки: 1-2 часа.

## 16. Когда воркер «не может» — это часто «не хочет ждать»

### Проблема
Воркер пишет «не могу починить карту» — но на самом деле он не дождался ответа пользователя. Тратит итерации на «давайте подождём DNS» вместо того чтобы **пойти сделать другую задачу или поставить блок**.

### Решение
Если воркеру нужна информация только от пользователя (DNS, пароль, визуальное подтверждение):
1. Сразу `kanban_block(reason="...", kind="needs_input")` — задача уходит в `blocked`.
2. Диспетчер берёт **другую** задачу.
3. Пользователь отвечает → диспетчер разблокирует.

**НЕ держать** воркера в ожидании. Это тратит concurrency.

## 17. Команда: распределение по 2+ дублёров на специальность

### Когда окупается
- 5+ задач в бэклоге на профиль
- 2+ задачи с разной специализацией (бэк: производительность vs API, фронт: UI vs a11y vs map)

### Когда НЕ окупается
- <3 задач в бэклоге — 1 воркер справится
- 1-2 профиля в команде (нет смысла дублировать)

### Конфигурация дублёра
- `description` (специализация) — задачи с пометкой `[quick]`, `[deep]`, `[security]` распределяются лучше
- Тот же `model.default` и `fallback_providers` как у основного
- НЕ общий пул (мы обсуждали — пока не нужно, явное назначение понятнее)

## 18. Документация в Obsidian — не забывать обновлять

### Проблема
Воркеры меняют `.env`, добавляют сервисы, меняют API endpoints — но `docs/Развертывание/Реквизиты_доступа_VPS.md` остаётся старой. Через 2 недели никто не помнит что где лежит.

### Решение
**В каждой задаче**, которая трогает инфраструктуру:
1. Обновить соответствующий `docs/Развертывание/*` файл
2. Добавить дату и краткое описание изменения
3. Если меняется `.env` — вынести комментарий в `docs/Архитектура/ENV.md`

См. также правило: **затирай старые пути/пароли** (например, при смене SSH-ключа) — не добавляй рядом новые.

## 19. Цепочка dev ↔ prod — что нельзя смешивать

### Правило
- **Локальный dev** (порт 3000, debug-логирование, демо-данные) — никогда не идёт в прод
- **Staging** (если есть) — для QA, e2e-тестов
- **Production** — только проверенный код, минимальные логи, мониторинг

### В JobMap
- Окружения не было — dev = prod на VPS
- Это **риск**: правка в проде без проверки
- Решение: добавить **staging** при росте (отдельный поддомен или порт)

## Контрольный чек-лист для нового проекта

Перед стартом работы с новой командой оркестраторов, проверь что:

- [ ] **goal_mode** включён в правилах (по умолчанию для сложных задач)
- [ ] Все профили имеют **fallback-провайдеров** (минимум 2)
- [ ] `failure_limit` = 4 в конфиге
- [ ] Есть **watchdog** для gateway/disk/RAM
- [ ] `docs/Архитектура/PROJECT_DIGEST.md` создан (3-6 KB, 5 секций)
- [ ] Создан `.github/workflows/deploy.yml` (или эквивалент CI)
- [ ] Все воркеры знают правило: **сам-мерж в main → kanban_complete**
- [ ] `kanban_list --status blocked` проверяется ежедневно (отмена дублей)
- [ ] Memory в `~/.hermes/profiles/<name>/memory/` — компактная, declarative
- [ ] Secrets (VPS, API ключи) — в GitHub Secrets / внешнем vault, **не** в репо
