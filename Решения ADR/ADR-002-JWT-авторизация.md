# ADR-002: Авторизация через JWT

**Статус:** Принято  
**Дата:** 2026-07-22  
**Контекст:** Необходимо обеспечить безопасную аутентификацию и авторизацию пользователей (соискатели и работодатели).

## Решение
Использовать **JWT (JSON Web Tokens)** с парой токенов:
- **Access token** — короткоживущий (15-30 минут), передаётся в заголовке `Authorization: Bearer <token>`
- **Refresh token** — долгоживущий (7-30 дней), хранится в БД, используется для получения нового access token

### Поток аутентификации
1. `POST /api/v1/auth/register` — регистрация, хеш пароля через `bcrypt`
2. `POST /api/v1/auth/login` — проверка пароля, выдача пары токенов
3. `POST /api/v1/auth/refresh` — обмен refresh token на новую пару
4. `GET /api/v1/auth/me` — получение текущего пользователя по access token

### Безопасность
- Пароли хешируются `passlib[bcrypt]`
- Refresh token хранится в таблице `refresh_tokens` (связь с пользователем + срок)
- Access token НЕ хранится в БД (stateless)
- На фронте — axios-интерсептор автоматически подставляет Bearer token и обрабатывает 401

### Альтернативы
- **Session-based auth** — rejected: требует серверного хранилища сессий, неудобно для Capacitor (мобильное приложение)
- **OAuth2 social login** — отложено: усложняет MVP, будет добавлен позже

## Последствия
- Стандартный JWT — легко реализовать и тестировать
- Refresh token в БД даёт контроль над сессиями (можно отозвать)
- На фронте — Zustand store для токена + axios interceptor
- В перспективе — добавить OAuth2 (Google/GitHub) как отдельный провайдер
